# 正式使用执行计划（2026-09-07）

本计划把当前工作压缩为四个可独立验收的上线批次。目标不是把“路由存在”当成完成，而是让真实 SQLite、HTTP/WS、OpenResty、任务日志和回滚证据同时成立。`/www/apps/1Panel` 只读，所有实现和文档改动仅发生在 `apps/workmesh-server`；前端没有变更时不重新编译。当前真实登录抽样已确认服务可达、网站 1 条、运行时 6 条、日志 40,741 条；写请求缺少 CSRF 会被真实拒绝，完整业务闭环仍按以下批次执行。

## 优先级（面向“先正式可用 3~4 个核心点”）

| 优先级 | 批次 | 正式使用价值 | 当前状态 | 放行条件 |
| --- | --- | --- | --- | --- |
| P0 | 静态网站 + 域名 + HTTPS | 最快形成可访问的主站/次站基础能力 | `ready-for-isolated-drill` | API CRUD、目录/日志、域名访问、证书、`nginx -t`、删除清理全部有证据 |
| P1 | 反向代理 + 六类运行时网站 | 覆盖主要业务部署和运行环境 | `blocked`（上游/镜像缺失） | 真实上游、容器生命周期、网站访问和 SQLite 任务日志闭环 |
| P2 | 升级、迁移、回滚 | 保证上线后可安全更新和恢复 | `ready-for-isolated-drill` | 候选制品验签、隔离库双启动幂等、备份、原子替换、健康检查和回滚演练 |
| P3 | 日志审计 + WS/主次节点 | 完成运维可观测性及终端/节点协作 | `partial` | 七类日志可追溯，4 条 WS 序列和主次节点 fencing/断线恢复真实通过 |

正式上线建议先锁定以下四个可交付点：

1. **站点可访问**：静态站点、主/次站点角色、域名绑定和 HTTPS（P0）。这是用户立即可感知的核心能力。
2. **业务转发与运行时**：反向代理及至少实际使用的运行时闭环（P1）。没有真实上游和容器生命周期，不应宣称业务可用。
3. **可回滚发布**：SQLite 迁移幂等、备份、验签、原子替换和回滚演练（P2）。这是上线安全底线，应与 P0/P1 同批验收。
4. **可审计运维**：系统/主机 SSH 日志契约、任务日志、WS 终端及主次节点协作（P3）。其中系统日志和 SSH 日志当前为硬阻断，必须明确标记为未完成，不能用空数据或模拟响应放行。

P0 是第一放行点；P1 是业务完整可用点；P2 是生产发布点；P3 是运维和多节点完整性点。任何批次缺少真实凭据或外部资源时保持 `blocked/not-run`，不使用 JSON fixture、固定成功或固定空列表代替。

## 并行席位与细分任务

最多 4 个席位（主控 + 3 个智能体）。每个智能体只修改自己的文档或代码目录，不执行全量门禁；所有全量测试由主控统一执行。

| 席位 | 任务 ID | 具体工作 | 交付物 | 依赖 |
| --- | --- | --- | --- | --- |
| 主控 `/root` | INT-00 | 冻结快照、冲突审阅、统一门禁、发布/回滚和状态汇总 | `integration-test-latest.md`、本计划、`STATUS.md` | 所有专项交付 |
| 智能体 A | WEB-01~06 | 静态 CRUD、反代、运行时站点、子站点、stream、HTTPS/WAF 设置矩阵；只读核对配置归属 | 网站就绪报告和逐项证据模板 | 隔离域名、管理员会话、真实上游 |
| 智能体 B | RUN-01~06 | Go/Node/Python/Java/.NET/PHP 生命周期请求序列；PHP FPM、扩展、Supervisor 专项 | 运行时就绪报告和清理清单 | 隔离 Docker、镜像、端口 |
| 智能体 C | OPS-01~04 | 升级迁移双启动、制品签名/备份/回滚；日志七分类查询；WS/主次节点契约审阅 | 升级报告、日志/WS 矩阵 | 候选制品、凭据和维护窗口 |

席位完成后立即轮换下一个未完成任务，不重复创建同一专项。若外部资源尚未提供，智能体交付可执行命令、字段和明确阻塞证据，不伪造通过结果。

## P0 静态网站执行序列

1. 主控记录源码集合哈希、运行制品哈希、SQLite `schema_migrations`、WAL/SHM 和 `nginx -T` 摘要。
2. 为每个案例分配独立 `<prefix>.cs.sopvip.com`，确认 DNS、80/443 可达；不得复用 `znmp.sopvip.com`。
3. 唯一集成负责人使用管理员会话执行 `POST/GET /api/v2/websites*` 创建、详情、域名、目录、默认文档、启动/停止/重启、访问日志和删除；每一步记录 `code/data/message`、SQLite 行和任务 ID。
4. 通过 `curl --resolve` 验证 HTTP 正文、404、停止后的真实错误和恢复后的 200；检查 `site.conf` 的 `server_name/root/index`，运行 `docker exec workmesh-openresty-waf nginx -t`。
5. 使用 Let's Encrypt HTTP-01 为具体前置域名签发/安装证书，核验 SAN、私钥匹配、SQLite SSL 外键和 443 访问；续期失败必须保留旧证书并可恢复。
6. 删除站点后确认 SQLite、目录、include 和日志无孤儿；保存脱敏证据后才标记 P0 `pass`。

## P1 业务运行序列

先执行真实运行时创建，再创建网站绑定；每一类都执行“创建→详情→启动→停止→重启→日志/任务→更新/备注→删除→重启恢复→同名重建→域名访问”。容器实际状态、端口和任务日志必须与 SQLite 一致。反代额外验证请求头、WebSocket Upgrade、超时和上游停止时的 502；PHP 额外验证 FPM status、扩展事务、php.ini、Supervisor 和慢日志。

## P2 发布序列

1. 候选二进制执行 SHA-256、Ed25519 验签和 512 MiB 大小限制；前端无变更不构建前端。
2. 停止服务前备份二进制、配置、SQLite、WAL、SHM，并在隔离目录启动两次：第一次应用迁移，第二次必须 `noop`；核对旧数据和新字段。
3. 维护窗口内由人工批准的 root 流程原子替换 `/opt/workmesh-server/bin/workmesh-server`，启动后检查 systemd、`/health`、`/ready`、SQLite 三项完整性、OpenResty 和 P0 站点。
4. 任一就绪、5xx、迁移或完整性失败立即停止服务，保存失败证据，原子恢复同一批次制品和数据库；回滚后再次执行健康和 P0 访问检查。

## P3 日志与 WS 验收

日志必须覆盖操作、访问、系统、任务、主机、登录、网站七类：真实操作产生记录，查询支持分页/过滤/时间范围，敏感字段脱敏，保留策略可验证，不能返回固定空数组。WS 必须验证终端连接、鉴权、消息序列、命令输出、关闭码、超时、断线重连和资源释放；主次节点还需验证注册、心跳、签名、epoch/fencing、任务透传和旧 epoch 拒绝。

## 统一门禁与时间盒

代码快照变化后，主控按固定顺序执行：

```text
GOWORK=off go test ./...
GOWORK=off go test -race ./...
GOWORK=off go vet ./...
node --test test/contract/*.test.mjs
node test/contract/route-scan.mjs check ...
git diff --check
SQLite 只读完整性 + systemd/health/ready/OpenResty
```

获得外部授权后的首个 5 小时按以下时间盒推进：0–30 分钟冻结与备份；30–120 分钟完成 P0 静态闭环；120–240 分钟并行完成 P1 运行时/反代；240–300 分钟执行 P2 隔离迁移和发布前回滚演练。P3 在资源允许时并行取证，不能挤占 P0/P1 的清理和回滚时间。

## 当前必须补齐的输入

- 管理员 Cookie/Bearer/API Key 和 CSRF 配对值（只注入环境变量）。
- 每种网站类型独立的 `*.cs.sopvip.com` 前缀、真实目录和清理窗口。
- 可清理的 Docker daemon、六类镜像、PHP-FPM/FastCGI 和反代/stream 上游。
- 候选 Linux 二进制、Ed25519 签名/公钥、维护窗口及 root 发布脚本批准。
- 主次节点地址和凭据、允许的 WS/终端测试资源。

在这些输入到位前，当前可以继续做代码/契约审阅和只读检查，但不能宣称正式上线；下一次动作应由主控根据输入完整性选择 P0 或 P2 隔离演练入口。
